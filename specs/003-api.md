# API

## Overview

The HTTP surface a caller codes against: upload or name a file, submit
a parse, watch it, read the document whole or one object at a time,
cancel or retry. The contract is small on purpose. Every field it
accepts changes what happens; a field it does not implement is refused.
The contract itself is `api/openapi.yaml`. This spec explains it, and a
test holds the server to it.

## Current state

The earlier service exposed `POST /v1/parse` with a result read by
polling, an upload endpoint, and an error envelope with stable codes.
The envelope, the idempotency header, the cursor scheme and the upload
limits are carried over. Four things are not: the result was a rendered
text with the layout hidden behind an unpublished route, several
request fields were accepted and did nothing, cancel recorded a state
without stopping work, and the event stream sent one snapshot. This
spec replaces those.

## Design

### Three kinds of choice

What a parse does is fixed at submit by a small set of options, each
independent of the others: which pages, which reader, in which class
and with which priority, how many failed pages are tolerated, and by
when. What a caller sees of the result is chosen when the result is
read: the format, the pages, how tables are written, how the document
is cut into chunks. Reading a result in another form never runs the
parse again. Extraction is neither: it is a request of its own against
a parse ([[011-structured-extraction]]), so a new schema needs no new
parse and no page is read twice.

### Routes

All routes sit under a base path, `/v1` by default, set by
`LECTIO_BASE_PATH` so a deployment can mount the surface under a prefix
of its own. Every route below the base path needs a bearer token,
except `GET /openapi.yaml`, which serves the contract. `GET /healthz`
sits outside the base path and needs no token. The readiness and
version probes of [[015-observability]] come with the durable server.

| Method and path | Purpose | Answers | Action asked |
|---|---|---|---|
| `POST /files` | upload a source; `200` with the existing File on a content match | 200, 201, 400, 413, 415, 422 | `file.create` |
| `GET /files/{file}` | File metadata | 200, 404 | `file.read` |
| `DELETE /files/{file}` | delete the snapshot; refused while a parse that has not ended reads it | 204, 404, 409 | `file.delete` |
| `POST /parses` | submit; `202` with the Parse, `200` when it ended within the wait | 200, 202, 400, 402, 404, 409, 413, 415, 422 | `parse.create` |
| `GET /parses` | list, newest first, filtered by `state`, `file`, `origin.path` and `label` | 200, 400 | `parse.list` |
| `GET /parses/{parse}` | state, progress, usage, error | 200, 404 | `parse.read` |
| `DELETE /parses/{parse}` | delete the parse and everything it wrote; refuses a parse that has not ended | 204, 404, 409 | `parse.delete` |

| `GET /parses/{parse}/pages` | page list with state, without blocks | 200, 404 | `parse.read` |

| `GET /parses/{parse}/blocks` | the bulk read: every block of the pages read so far, one JSON object per line | 200, 400, 404, 409 | `parse.read` |
| `GET /parses/{parse}/blocks/{ref}` | one block | 200, 400, 404, 409 | `parse.read` |

| `POST /parses/{parse}/figures` | describe the figures of a parse that has ended | 200, 202, 400, 404, 409, 413 | `parse.create` |
| `GET /parses/{parse}/figures` | the parse's figures, described or not, and the run that describes them | 200, 404 | `parse.read` |
| `GET /parses/{parse}/chunks` | chunks, one JSON object per line | 200, 400, 404, 409 | `parse.read` |
| `POST /parses/{parse}/fields` | extract an object in the shape of a schema | 202, 400, 404, 409, 501 | `parse.create` |
| `GET /parses/{parse}/fields` | the parse's extractions, each as it stands | 200, 404, 501 | `parse.read` |
| `GET /parses/{parse}/fields/{name}` | one extraction, its citations as refs or with their page and box | 200, 400, 404, 501 | `parse.read` |
| `GET /readers` | the configured readers and what each accepts, the policy's first marked `default` | 200 | `reader.list` |
| `GET /usage` | meters ([[013-limits-and-usage]]) | 200, 400, 501 | `usage.read` |

| `GET /openapi.yaml` | the contract, without a token | 200 | none |

Any route may also answer `401`, `403`, `429`, `500` and `503`. A route marked
planned is in the contract with `x-lectio-status: planned`, is routed
and authenticated, and answers `501 not_implemented` until it is
built, so a client written against the contract finds every address
from the first version on. No route is marked today. A route that one
of the 2 servers does not build lists the `501` too, without the mark,
and its description says which server answers it: `retry`, `events`,
`usage`, `queue` and the 3 routes of an extraction are built over the
task store, which a development server does not have. Describing
figures is built in both. An address that is not routed is `404
not_found`, and one that is routed under another method is `405
method_not_allowed` with an `Allow` header.

The action is what the route asks the authorizer before it acts
([[012-identity-and-authorization]]). 3 routes ask `parse.create`
about a parse that exists: a retry, a figure run and an extraction each
queue model work on it. Of the limits on the allow, a figure run and an
extraction are held to `readers`: a describer or an extractor the
request names outside them is `403 reader_not_permitted`. The work
itself is the stored parse's owner's and runs in the group the parse
was admitted to, held to that group's `max_running` as its last submit
wrote it; it counts no page against the group's day
([[011-structured-extraction]], [[013-limits-and-usage]]). A retry is
held to the bounds of the group its parse was admitted to (Retry,
below). A read of everything a
parse produced asks `parse.read`.
The table is kept as data beside the code that asks, and a test holds
it equal to this one and to the contract's routes.

### Submit

```json
{
  "source": { "file": "fil_01J..." },
  "origin": { "store": "example", "path": "reports/q3.pdf", "version": "4" },
  "pages": "1-3,7",
  "reader": "default",
  "languages": ["de", "en"],
  "class": "interactive",
  "priority": 0,
  "allow_failed_pages": 0,
  "deadline": "10m",
  "reuse": true,
  "labels": { "batch": "2026-10" }
}
```

- `source` is exactly one of `{"file"}` or `{"url"}`
  ([[014-sources-and-retention]]).
- `origin` is provenance the caller supplies and Lectio stores, returns
  and filters on, and never interprets. `store` and `version` hold at
  most 64 bytes, `path` at most 1,024.
- `pages` selects pages, counted from 1, as ranges and numbers separated
  by commas. An open range such as `5-` runs to the end, and a range
  past the end is clamped to the document. The syntax is checked at
  submit; a selection that names no page of the document fails the
  parse with `invalid_pages` once the pages are counted.
- `reader` names a configured reader. Naming one pins it: the parse
  does not fall back to another ([[007-model-capacity]]). Absent, the
  routing policy decides. A name that is not configured is `400
  reader_not_found`.
- `languages` are hints for the reader, most likely first: at most 8
  tags of at most 35 bytes.
- `class` is `interactive` (default) or `batch`. Interactive work goes
  ahead of batch work and never starves it.
- `priority` orders the caller's own pages and is capped by the limits
  on the allow ([[006-fairness-and-priority]]): a priority outside the
  bound is `400 invalid_request` on `priority`, and with no bound named
  or configured the one priority is 0. It never moves one caller ahead
  of another: the caller is chosen first and the caller's page second,
  so nothing a caller queues, however much or at whatever priority,
  changes which caller is served.
- `allow_failed_pages` (default 0) is how many pages may fail and still
  leave the parse `succeeded`. Pages that were read are kept either way
  ([[005-parse-graph]]).
- `deadline` bounds the parse's wall clock from submit, as a duration
  above zero and at most `LECTIO_MAX_DEADLINE`. Past it the parse fails
  with `deadline_exceeded`. A parse submitted with none takes
  `LECTIO_MAX_DEADLINE` as its deadline, so nothing waits without bound
  ([[004-durable-tasks]]). The default of one hour is short for a batch
  parse that waits its turn behind others; a longer default for the
  batch class is open.
- `reuse` (default `true`) says whether a page that an earlier parse
  of the same caller read whole, from the same bytes with the same
  readers, is taken from that read ([[002-object-model]]). The submit
  makes a parse of its own either way, with its own id, labels and
  origin. A page that was taken says `reused: true`, the parse counts
  such pages in `progress.pages_reused`, and no model is called for
  them. With `reuse: false` every page is read.
- `labels` are the caller's own keys and values, at most 16, each key
  and value at most 256 bytes.
- A body with a member the contract does not name, at any depth, is
  `400 unknown_field` with the member in `details.field`.

There is no output option and no extraction option on a submit. Both
were submit options in the first draft of this spec. A rendering or a
chunking that is fixed at submit forces a second parse to see the same
pages another way, and an extraction that is fixed at submit forces a
second parse to ask a second question, so both moved to where they
cost nothing.

Reuse was the return of a whole earlier parse in the first draft: a
submit that matched one by content and an options fingerprint answered
`200` with that parse and `reused: true`. It gave the caller a parse it
had not asked for: the new submit's labels and origin were dropped, a
list filtered by them never found it, a submit that tolerated no failed
page was answered with a parse that had some, and deleting the parse
deleted it for both. Reuse is now of the reading and not of the parse.

`Idempotency-Key`, at most 255 bytes, makes a submit safe to repeat
for 24 hours. The key and the parse are written together under a
unique constraint, so two concurrent submits with one key create one
parse. The same key with a different body is `409
idempotency_conflict`.

`Prefer: wait=<seconds>`, at most 60, holds the answer until the parse
ends or the wait runs out. The answer is `200` when the parse ended
and `202` when it did not, and carries `Preference-Applied`. A short
document is then one request, and nothing about a long one changes.

### Parse

```json
{
  "id": "prs_01J...", "owner": "https://issuer.example|alice",
  "state": "running",
  "class": "interactive", "priority": 0,
  "file": "fil_01J...", "origin": { },
  "progress": { "stage": "reading", "pages_total": 120, "pages_done": 37, "pages_failed": 0, "pages_reused": 12, "waiting": "capacity" },
  "usage": { "pages": 37, "input_tokens": 412000, "output_tokens": 96000, "cost": "0.21", "currency": "USD" },
  "created_at": "...", "started_at": "..."
}
```

`state` is `queued`, `running`, `succeeded`, `failed` or `canceled`.
`progress.stage` is `queued`, `preparing`, `reading`, `assembling` or
`done`. `progress.waiting` says why nothing is moving when nothing is:
`turn` (other tenants are ahead), `capacity` (the model pool is full
or paused), or absent. `progress.pages_reused` is how many of the
pages done were taken from an earlier read, and is absent when none
was. A parse also returns the options it was submitted with,
`deadline_at` when it has a deadline, and `error` when it failed.

A parse that ended, however it ended, has a document. A failed parse
keeps every page that succeeded, with the failed pages marked. A parse
that was canceled or ran out of time keeps every page it read, and the
pages it did not reach are `skipped` ([[002-object-model]]). A parse
that could not start, because its file was gone or of a type that is
not read, has a document with no pages.

### Cancel

`POST /parses/{parse}/cancel` takes effect at once: the parse and its
waiting pages are canceled in the request's own transaction
([[004-durable-tasks]]), no further page is read, and a page being read
is abandoned and its result dropped. What was read stays readable, as
pages and as a document. Canceling a parse that has ended is `409
already_terminal`.

### Retry

`POST /parses/{parse}/retry` reads again the pages of a parse that
failed, and no other. It is for a parse that ended with its pages all
settled and at least 1 of them failed, whether the parse failed or
allowed them ([[005-parse-graph]]). The answer is `202` with the parse
as the retry left it: `running`, the failed pages open, and the pages
that were read readable as before. The retry is one transaction
([[004-durable-tasks]]): when it answers, the pages are queued.

| The parse | Answer |
|---|---|
| has not ended | `409 not_terminal` |
| has no failed page | `409 conflict` |
| ended before its pages had all settled: canceled, out of time, or with a file that could not be prepared or assembled | `409 conflict` |
| ended before its task rows were kept, or is past its retention | `409 conflict` |
| has an extraction or a figure queued or running | `409 conflict` |
| is in a group that holds `max_queued` parses that have not ended | `429 queue_full` |
| has more failed pages than its group's day holds | `402 budget_exhausted` |

`details.reason` says which. A parse that ended before its pages had
all settled is read again by a new submit of its file, which takes the
pages that were read from the earlier read ([[005-parse-graph]]). A
retry writes again the pages and the index of its parse, which an
extraction and a figure read, so it waits for them: the answer is
`409` until they have ended, and the caller asks again.

A retried parse keeps its id, its owner, its group and its project, its
class, its priority and the reader it pinned. It is held to the bounds
of its group as they stand, which the group's last submit wrote
([[006-fairness-and-priority]]), and its failed pages are reserved
again, of the day of the retry ([[013-limits-and-usage]]). The limits
of the retry's own allow change none of that: `parse.create` is asked
so that an authorizer can refuse the retry, and the parse does not
move. The parse has as long from the retry as its submit gave it.

### Reading a result

Results are addressed by object, and each is readable as soon as it
exists.

- A page is readable once it was read, while the parse is still
  running. A page not read yet is `409 page_not_ready`. A page the
  parse does not read is `404 page_not_found`. A page the parse ended
  without reading answers `200` with `state: skipped`.
- The document is readable once the parse has ended, in whatever
  state. While the parse runs it is `409 document_not_ready`.
- Both `409` answers carry `details.retryable: true`: the address is
  right and the answer is not there yet. `404` means it will not come.
  Since every parse that ends has a document, `document_not_ready` is
  never the answer for one that has ended.

`GET /parses/{parse}/document` takes the view as query parameters:

| Parameter | Values | Meaning |
|---|---|---|
| `format` | `json` (default), `markdown`, `text` | the index, or the content in reading order |
| `pages` | a selection, in the syntax of a submit's `pages` | limits a Markdown or text rendering to these pages |
| `tables` | `auto` (default), `markdown`, `html` | how a table is written in Markdown; `auto` writes Markdown unless a cell spans |
| `repeated` | `once` (default), `keep`, `drop` | whether running headers and footers are printed once, on every page, or not at all |
| `page_breaks` | `false` (default), `true` | whether a Markdown rendering marks where each page begins |

As JSON the document is its index: the pages without their blocks, the
spans, the outline, and usage ([[010-assembly]]). Blocks are read by
page, which keeps a long document out of one reply.

`GET /parses/{parse}/chunks` takes `by`, `section` (default) or `page`,
and `max_chars`, from 200 to 100,000 with a default of 6,000, and
answers `application/x-ndjson`, one chunk per line.

`GET /parses/{parse}/blocks` is the bulk read: every block of the pages
read so far, in page and reading order, as `application/x-ndjson`, one
block per line. A block's `ref` says which page it is on. It answers
while the parse runs, with what has been read, and takes `pages` to
limit the answer to a selection. Without it a caller that wants all of
a 3,000-page document makes 3,001 requests.

### Events

`GET /parses/{parse}/events` follows a parse as server-sent events,
until it ends. 3 kinds of event are sent:

| Event | Data | Sent |
|---|---|---|
| `page` | `page`, its `state` (`succeeded` or `failed`), and its `error` when it failed | once for each page that settles, in the order the pages settled |
| `progress` | the parse's `progress` | when the stream opens, and whenever the parse has changed since |
| `state` | the parse's `state`, and its `error` when it failed | when the stream opens, and whenever the state has changed |

`state` and `progress` say where the parse stands, so a client that was
away is told the latest and not each step between. A `page` event is
sent for every page, however long the client was away. A page that a
cancel or a deadline stopped did not settle and has no event: the
document lists it as `skipped`.

**The ids.** The task store counts the changes of a parse
([[004-durable-tasks]]). Its submit is change 1, and every change of
its state or of its progress is 1 more: the claim that starts it, the
settle of `prepare`, the settle of each page, its end, a cancel, a
retry. A page's row holds the change that settled it. An event's id is
3 times the change it reports, plus 0 for `page`, 1 for `progress` and
2 for `state`. So every event of a parse has an id of its own, the ids
only grow, and the events are sent in the order of their ids: the pages
by the change that settled each, then the progress and the state of
the parse's latest change. An id is computed from rows and from nothing
a process holds, so every replica gives an event the same id, before
and after a restart.

`Last-Event-ID` resumes after an id: the pages that settled after it
are sent, then the progress and the state when they are newer than it.
An id the stream did not send, one that is no number or is past the
parse's latest, is read as none, and the stream starts from its
beginning.

The change that settled a page outlives the page's task row. The rows
of a parse that ended with every page read are deleted, and the
changes of its pages are then kept beside the parse, a few bytes a page
in one row per parse. The pages of a format that needs no reader have
no task: `prepare` wrote them, and each is 1 change after the one that
counted them, in the order of the selection. So a stream opened at any
time, on a parse that runs or on one that ended, sends the same events
under the same ids.

**The stream.** There is no `LISTEN` behind a transaction-mode pooler
and no bus between the processes, so a stream is a poll. Every second
it reads the parse's row and the pages that settled since, in one
statement and so from one snapshot, and sends what is new. Nothing is
kept between 2 polls but the id last sent, so any replica serves any
stream. Each open stream costs 1 statement per second on the API's
pool. The server

- names the delay to wait before connecting again in a `retry` field,
  which is its poll interval;
- sends a comment line when it has sent nothing for 15 seconds, so a
  proxy that cuts idle connections leaves the stream of a waiting parse
  open;
- ends the stream after the `state` of a parse that has ended;
- ends a stream it has held for 5 minutes, whatever the parse does. The
  client connects again with the id of the last event it saw. The bound
  is also the longest a decision of the authorizer is held: `parse.read`
  is asked when a stream opens;
- bounds one write at 10 seconds, so a client that stopped reading does
  not hold a stream open.

A read of the rows that fails before anything was sent is answered as
any error is. After that the answer is the stream: a failure ends it,
and the client connects again.

### Uploads

`POST /files` takes a raw body with its media type in `Content-Type`,
or `multipart/form-data` with one part named `file`. `?name=` gives
the file a name, which only helps tell its type when the content does
not. The body is streamed to the object store while it is hashed; it
is never buffered whole. The size limit is `LECTIO_MAX_FILE_BYTES`
(default 256 MiB) or the allow's lower figure. A body over it is `413
file_too_large`, and one whose type is not supported is `415
unsupported_media_type`.

### Errors

```json
{ "error": { "code": "unknown_field", "message": "The request has a field that is not recognized.", "details": { "reason": "the body has a member \"mode\" the contract does not describe", "retryable": false, "field": "mode" } } }
```

One code to branch on, one fixed sentence for a person in `message`,
and `details` for a developer: `reason` says what happened in this
instance, `retryable` whether the same request may succeed later, and
`field` which member of the request the error is about, when it is
about one. The shape is the shared envelope of
`latere.ai/x/pkg/httpjson`. An error nobody classified is `500
internal` with no reason: its text is logged and not returned.

| Status | Codes |
|---|---|
| 400 | `invalid_request`, `unknown_field`, `invalid_pages`, `invalid_schema`, `reader_not_found` |
| 401 | `missing_token`, `invalid_token` |
| 402 | `budget_exhausted` |
| 403 | `forbidden`, `reader_not_permitted` |
| 404 | `not_found`, `file_not_found`, `parse_not_found`, `page_not_found`, `block_not_found` |
| 405 | `method_not_allowed` |
| 409 | `page_not_ready`, `document_not_ready`, `conflict`, `idempotency_conflict`, `not_terminal`, `already_terminal` |
| 413 | `file_too_large`, `too_many_pages` |
| 415 | `unsupported_media_type` |
| 422 | `source_unreachable` |
| 429 | `rate_limited`, `queue_full` |
| 500 | `internal` |
| 501 | `not_implemented` |

Retryable are `page_not_ready`, `document_not_ready`,
`source_unreachable`, `rate_limited`, `queue_full` and `internal`.
The table is the server's own (`problems` in `internal/httpapi`), and
a test holds it equal to the contract's list of codes. Two more codes
are in both, with what they report
([[012-identity-and-authorization]]): `authorizer_unavailable`, `503`,
which is retryable, and `capability_unsupported`, `422`. One joins them
with what it reports: `store_unavailable`, `503`
([[004-durable-tasks]]).

Where a refusal that comes from the caller's allow lands: a class the
allow does not name is `403 forbidden` with `details.field` `class`, a
reader it does not let the caller pin is `403 reader_not_permitted`, a
file over its size is `413 file_too_large`, and a group with no page
left of its day is `402 budget_exhausted` on the submit. A parse that
selects more pages than the allow lets one parse select, or more than
its group's day holds, is accepted and fails where its pages are
counted, with `too_many_pages` or `budget_exhausted` on the parse.

Failures of the work land on the parse, a page or a field, not on the
submit: `file_not_found`, `file_too_large`, `invalid_pages`,
`document_corrupt`, `unsupported_media_type`, `too_many_pages`,
`source_unreachable`, `page_unreadable`, `reader_unavailable`,
`budget_exhausted`, `deadline_exceeded`, `schema_not_satisfied`,
`internal`. There the shape is `{"code", "detail"}`.

### Lists

`GET /parses` pages by a cursor, `limit` 50 by default and 200 at
most. Identifiers sort by creation time ([[002-object-model]]), so the
list is newest first by id and `next_cursor` is the last id of a page.
A caller treats the cursor as opaque. `label` is `key=value`, may
repeat, and every one must match. The authorizer's `filter` narrows a
list to the owners and labels the caller may see.

## Open

- **The name of the extraction resource.** `fields` names a whole
  extraction: one named object in the shape of a schema, which itself
  has fields. `extractions` would say what it is. Taken as the default
  on 2026-10-04, before a first release froze the contract: the name
  stays `fields`. The routes are built under it, so a rename is now a
  breaking change.
- **The default deadline of a batch parse.** One value of
  `LECTIO_MAX_DEADLINE` serves both classes, and one hour is short for
  batch work that waits behind others.
- **Rendering while a parse runs.** Markdown and text come from the
  document, which exists when the parse ends. The pages read so far
  are readable one by one and in bulk as blocks, and not as Markdown.
- **A notice when a parse ends.** The event stream tells a client that
  holds a connection. A callback to an address the caller names is not
  designed.
- **One statement per stream.** Each open event stream reads its parse
  once a second. One statement that reads the parses of every stream of
  a process would cost the same for 1 stream and for 100.

## Not in this spec

A client library and a command line client; both follow once the
surface is implemented and are thin over it. Administrative writes
(changing a group's weight, pausing a pool) are configuration in the
first version ([[016-distribution]]). Filtering a list by creation
time.

### Figures

A reader that finds a figure says where it is, and may not say what it
shows. Two routes close that gap, and neither reads a page again.

`GET /parses/{parse}/blocks/{ref}/image` is a block's image: the page
image the reader saw, cut to the block's box. For a figure that is the
figure itself, and it works for any block that has a box. A block with
no box, and a block of a page that was not read from an image, is
`404 block_not_found`.

`POST /parses/{parse}/figures` asks a describer what each figure
shows ([[008-readers]]). It is a request against a parse that has
ended, the way an extraction is, and not a submit option: figures can
be described later, for some pages, by another describer, with no page
read again.

| Member | Meaning |
|---|---|
| `pages` | limits the run to figures on these pages, in the syntax of a submit's `pages`; absent means all |
| `describer` | the name of a configured describer; naming one pins it; absent, the routing policy's describe chain decides |
| `redo` | describes again a figure that already has a description, and takes none from an earlier run; default false |

The body may be left out. A member the contract does not name is
`unknown_field`. A run describes every figure block on the selected
pages that has a box, sits on a page read from an image, and has no
description yet. Each figure is one call, queued with the pages of
every parse and taking its owner's turn. A figure described once from
the same bytes by the same describers is not described again by a later
parse, and is counted in the run's `reused`.

The answer is `202` with the listing below, or `200` when
`Prefer: wait=<seconds>` held it until the run ended. One run at a
time: a request while one is in flight is `409 conflict`. A parse that
has not ended is `409 not_terminal`. With no describer configured, or
one named that is not, it is `400 reader_not_found`.

A run describes at most 1,000 figures. A request whose pages hold more
than the run would describe is `413 too_many_pages` and starts
nothing: the caller names fewer pages, and describes the parse a range
of pages at a time. A figure keeps its description from run to run, and
one that has a description does not count unless `redo` is true, so
the runs over a long parse add up. The bound is on what one request
queues and writes: in the durable server a run is 1 row and 1 task for
each figure, written in one transaction under the lock every worker's
exchange waits for ([[004-durable-tasks]]). 1,000 figures are 2,000
rows, fewer than the task rows the `prepare` of a parse at the default
limit on pages writes under the same lock, and 1,000 calls, which the
time a run has is enough for ([[013-limits-and-usage]]).

`GET /parses/{parse}/figures` lists every figure block of the parse
with its `ref`, `page`, `box`, `text`, and, once described,
`description` and `figure`. `run` is absent until a run was started,
and then holds `state` (`running`, `succeeded`, `failed`), `total`,
`done`, `failed`, `reused`, `usage` and its times. A run succeeds when
it described any figure it set out to, and fails only when it described
none; a figure it lost carries `error`, a problem whose code is
`figure_unreadable`, `reader_unavailable`, `budget_exhausted`, or, from
a key endpoint that issues the group no key, `reader_not_permitted`
([[013-limits-and-usage]]). A run says what it lost itself: a later run
that does not take a figure an earlier one lost lists that figure with
no error.

**In the durable server** a run is rows and tasks
([[004-durable-tasks]], [[005-parse-graph]]). The request reads the
pages the run takes, 16 at a time and no further once it has found
more figures than a run describes, and reads no description: which
figures have one is on the rows of the runs before. It writes, in one
transaction, the run, a row per figure and a task per figure, `figure-<ref>`, in the parse's group and
project, in its class and at its priority, in the order of the figures.
When it answers, the figures are queued. Each task is claimed for the
describer the request named, which pins it, or for the first describer
of the policy's `describe` chain that is not passed over, takes a slot
in that reader's pool, is charged its `cost`, and is read with the key
of the parse's group. What its describer answers follows the table of
reader errors: a rate limit is a wait, a failure that may pass spends
an attempt, and a describer that declines the figure passes it down the
chain. A figure that ends its workers fails with `figure_unreadable`.

A description is an object of its own, `figures/<ref>.<token>.json`,
whose key the figure's row holds, and a page's stored result is left
as its reader wrote it. Every read of a block writes the description
onto it: the block, its page, the bulk read, the listing, and the
document's Markdown and text. A parse none of whose figures was
described costs a read nothing more. A description is kept per owner
under what was described, and a later run of the owner over the same
figure copies it under a key of its own and calls no describer.

A run has as long as a parse submitted with no deadline has. The
figures it has not described by then are lost to it with
`reader_unavailable`, and it ends with the ones it described. A delete
of the parse drops the run and its tasks with it, and a retry of the
parse waits for the run to end (Retry, above).

### Fields

The 3 routes of an extraction are [[011-structured-extraction]]: what a
request takes, how it runs, and what a field holds. Of the surface:

- `POST` answers `202` with the field, `pending`, and nothing else is
  ever in that answer: the extraction is a task. There is no `Prefer:
  wait` on it.
- `GET /parses/{parse}/fields` lists the fields by name, each as it
  stands, with its object once it has one.
- `GET /parses/{parse}/fields/{name}` answers `404 not_found` for a
  name the parse has no field of, and `400 invalid_request` for a
  `resolve` that is not `true` or `false`.
- The document's index lists the names of the fields that were filled,
  in `fields`.

## Implementation status

Built, in `internal/httpapi`, whose handlers serve from a backend. Two
exist: the memory store with the in-process runner, which is a
development server, and `internal/durable`, over Postgres and an object
store with parses run by worker processes. The cases of the contract
run over both, with every response held to `api/openapi.yaml`. What
follows holds for both unless it says otherwise:

- Every route of the table that is not marked planned, with the
  statuses and codes above, and the error envelope.
- Submit with every option above, the syntax check of `pages`, reuse
  by page, `Idempotency-Key`, and `Prefer: wait`.
- Results by object, the bulk read of blocks, the read-time views of
  the document, and chunks.
- A document on every terminal state, with the pages a parse did not
  reach recorded as `skipped`.
- A block's image, and the request that describes a parse's figures
  with its listing: in the in-process runner of a development server,
  and as a task per figure in the durable server.
- `priority` as the contract states it, in the in-process runner:
  owners take turns, one page each, within a class; priority orders an
  owner's own pages; and one page in five is a batch page when both
  classes wait. This is the fair queue's shape with every weight at
  one. It keeps no account of what each owner was served
  ([[006-fairness-and-priority]]).
- A contract test that walks the router against `api/openapi.yaml`,
  holds the two lists of error codes equal, and checks the status and
  the body of every response the end-to-end tests receive against the
  contract's schemas.
- Authentication and authorization on every route of the table
  ([[012-identity-and-authorization]]): the bearer is verified or is
  the development token, the route asks the action of its row before
  it acts, a planned route included, and the limits of a create's allow
  are held. `401`, `403`, `402 budget_exhausted`, `429 queue_full`,
  `422 capability_unsupported` and `503 authorizer_unavailable` are
  answered.

- In the durable server: `Idempotency-Key` held for 24 hours and
  unique per owner in the database, so two submits with one key at once
  make one parse; a parse submitted with no deadline takes
  `LECTIO_MAX_DEADLINE`; `Prefer: wait` answered by reading the parse's
  row; cancel in the request's own transaction; and a document for
  every parse that ended, read from the index `assemble` wrote or, for
  a parse that was canceled, ran out of time or could not start, made
  from its task rows when it is read.
- In the durable server, the 4 routes that are built over the task
  store. `retry` as the section above states it, in one call of one
  function. `events` as a poll of one function, with the ids, the
  comment, the bounds and the resume above; the poll interval, the
  silence before a comment and the bound on a stream are constants of
  `internal/httpapi`, and no setting. `usage` and `queue` as
  [[013-limits-and-usage]] and [[006-fairness-and-priority]] state
  them, each asking with the owner and the group its request names and
  narrowed by its allow's filter.

- In the durable server, the 3 routes of an extraction
  ([[011-structured-extraction]]), each asking its action about the
  stored parse before it acts.

Remaining:

- In a development server `retry`, `events`, `usage`, `queue` and the 3
  routes of an extraction answer `501 not_implemented`. Each is built
  over the task store: its runner drives a parse once and keeps nothing
  of one that ended, numbers no change, has no meter, no group and no
  pool, and keeps nothing between 2 calls of an extraction. An
  extraction is checked before it is answered, so a request that is
  malformed is told so by either server. Every route of the table is
  served by the durable server.
- `rate_limited` is never answered: submits per minute are not built
  ([[013-limits-and-usage]]). A submit cannot name an owner
  ([[012-identity-and-authorization]]).
- An upload is read whole by the API and then written to the object
  store, not streamed, and a URL source is fetched inside the submit
  request and not by `prepare`.
- `progress.waiting` is in the contract and is never set.
- In a development server the idempotency key does not expire, a parse
  submitted with no deadline has none, and cancel sets a flag and
  cancels the runner's context for the parse.
- A page of a parse that ended without `assemble` is served as its
  task wrote it: the running headers and footers are marked in the
  document's renderings and not on the page read by itself.
